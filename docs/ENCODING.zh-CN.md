# 编码：字节和毫秒到底花在哪

这里所有数字都来自 `krd --bench`——它跑真实的瓦片流水线（提取 → zlib → base64 → 转义序列），
不需要终端、不需要屏幕、不需要任何权限。改动 `Render.swift` 之后重跑一遍，产生下面表格的命令是：

```sh
swift build -c release
.build/release/krd --bench --pane 137x44 --cell 17x33            # 新默认：8x4 瓦片、f=24
.build/release/krd --bench --pane 137x44 --cell 17x33 \
                      --tile 16x8 --format rgba                  # 0.1.1 的默认值，用于对比
```

`--pane 137x44 --cell 17x33` 表示 137×44 格、每格 17×33 px 的窗格，即最初测量用的 2329×1452 px
画面。列的含义固定，两次运行可直接对比：`serial ms` 是单核压缩所有脏瓦片，`parallel ms` 用
`DispatchQueue.concurrentPerform`（线上路径用的就是这个），`bytes/frame` 是 base64 之前的编码载荷
（实际过 pty 的字节约为它的 1.33 倍）。

## 结果

基线（0.1.1：`--tile 16x8 --format rgba`）对比当前默认值（`8x4`、`f=24`）：

| 场景 | 0.1.1 字节 | 现在字节 | 变化 | 0.1.1 ms | 现在 ms |
|---|---|---|---|---|---|
| 一个字符（打字） | 2 132 | **727** | −66 % | 0.50 | 0.11 |
| 一整行文字 | 12 809 | **8 595** | −33 % | 0.64 | 0.28 |
| 全屏文字重绘 | 35 220 | 47 485 | +35 % | 1.23 | 0.84 |
| 全屏照片重绘 | 4 065 854 | **3 556 212** | −12.5 % | 15.57 | 4.46 |
| 600×400 拖动区域 | 1 478 503 | **1 077 640** | −27 % | 8.35 | 1.58 |

唯一的退步是**全屏**文字重绘：66 块 8×4 瓦片各自要付约 110 字节的图像头，zlib 也失去了 16×8 时
跨瓦片的上下文。全屏重绘只在改窗口大小、重连和第一帧发生，所以这是「罕见的 +23 %」换「每秒 20 次
打字路径的 −66 %」。想要回去就是 `--tile 16x8` 一个开关。

当前默认值下串行 vs 并行压缩：

| 场景 | 串行 ms | 并行 ms | 加速 |
|---|---|---|---|
| 一整行文字 | 1.19 | 0.28 | 4.2× |
| 全屏文字重绘 | 5.88 | 0.84 | 7.0× |
| 全屏照片重绘 | 39.80 | 4.46 | 8.9× |
| 600×400 拖动 | 12.41 | 1.58 | 7.9× |

压缩曾吃掉整个帧预算：0.1.1 时一帧照片全屏重绘要 ~80 ms，而 20 fps 的预算是 50 ms，所以重绘必卡。
现在它被编码部分（几块瓦片 0.3–1 ms）压住，而且并行段只处理真正变化过的瓦片。

## 为什么是这几个杠杆

**按瓦片选 zlib 级别（issue #3）**：全帧一个级别永远错——文字在 level 9 能压到 2 %，代价是两倍
CPU；而传感器噪声从 level 1 到 9 只多赚 1 %，CPU 却要 6 倍。`LevelPolicy` 记住每块瓦片上一帧的
压缩比，在 9（比值 < 7 %）、1（比值 > 13 %）和中间的 5 之间切换，并留 3 % 迟滞带防止抖动。
每块瓦片的第一帧付一次 level 5；之后在当前布局生命周期内选择是稳定的。

**用 f=24 而不是 f=32（issue #4）**：桌面是不透明的，alpha 字节恒为 255。去掉它少 25 % 原始字节，
噪声场景少 ~12 % 编码字节（恒定 alpha 列本来也能压，RGBA 之前吃了这个便宜），zlib 工作量少 10–20 %。
`--format rgba`（或 `KRD_FORMAT=rgba`）是给不支持 RGB 的终端的退路。

**每帧一个同步块（issue #6）**：把 `?2026h`/`?2026l` 从每块瓦片提到整帧外面——每帧 16 字节而不是
16 字节 × 66，一次提交而不是 66 次。环境变量读取从每瓦片移到 `init`：之前每帧要重建 66 次字典，
而那个值运行时根本不会变。

**抓帧不再整帧复制（issue #1）**：`Capturer` 现在在两个帧缓冲之间交替。往 `previous`
（以及 `Desk.previousFrame`）还引用着的缓冲里写，会让 `withUnsafeMutableBytes` 先复制整个 13.5 MB；
双缓冲后正在写的那个缓冲在构造上就是唯一引用，转换直接原地写。

## 采集缩放：`--scale`（issue #60）

`--scale 0.5` 让采集端每边只给一半像素（`SCStreamConfiguration.width/height` = pane 自身像素 × 缩放），
再由终端把图放大回同一个单元格框。其它都不动：

- **裁剪区**（`sourceRect`）不变——这不是 zoom；
- **placement 单元格框**（每 tile 的 `c=8,r=4`）不变，画面仍然精确铺满 pane：`--record` 在 scale 1 下
  出 1020×627 的原始帧、0.5 下出 510×314，而转义流里两次都是 `c=8,r=4` 的 placement、图像分别是
  136×132 与 68×66 px；
- **指针映射**不变，因为 SGR-Pixels 坐标是 **pane** 的网格，不是图像的。同一个终端像素点下去，TextEdit
  的光标在两种缩放下落在同一个偏移（两个测试点分别是 86 与 948），而故意加倍偏移的像素落到别处。

代价是清晰度：0.5 下一个 13 点的字形每边只有一半像素，文字会明显发虚——终端放大替代不了真像素。这是
一笔交易，不是白送的收益，所以默认是 1。

实测（macOS 26.6 虚拟机，pane 60×19 格、每格 17×33 px，静止桌面；`--bench` 用固定的 813-tile photo
布局）：

| | scale 1 | scale 0.5 | scale 0.25 |
|---|---:|---:|---:|
| 采集像素 | 1020×627 | 510×314 | 255×157 |
| `--bench` photo wire | 13.57 MB | 3.41 MB（**3.98×**） | 0.86 MB（**15.7×**） |
| 实时字节/秒（桌面） | 3.08 MB/s | 1.02 MB/s | 0.23 MB/s |
| CPU（`ps %cpu`） | 17.5 % | 8.4 % | 3.9 % |
| `bad` 帧 | 0 | 0 | 0 |

实时倍率是 3.2× 而不是 3.98×，因为静止桌面的字节主要是每帧的 framing 和真正变化的 tile；bench 那个是
干净的数字。自动的「链路吃紧先降 scale」策略故意不在这里：先把 flag 和数字做出来。

## 怎么量一次改动

```sh
.build/release/krd --bench --pane 137x44 --cell 17x33 --log /tmp/bench.log; cat /tmp/bench.log
```

`--bench` 每个场景取 6 轮里的最好成绩（避免调度噪声获胜）然后退出。合成场景是固定的：带字形笔画的
扁平 UI，以及完全没有 LZ77 匹配的哈希噪声。新增场景时，把对应行补进上面的表。
