# 脏矩形重估（issue #7）

**状态：** 重估，不是计划。**建议：关闭 #7** —— 它赖以成立的字节论据已经被 #3 + #5 打过，
而剩下的是 50 ms 帧里的 0.3 ms，代价却要撞上整个设计所依赖的那个不变量。
**English:** [research-dirty-rects.md](research-dirty-rects.md)

原始笔记：[#7](https://github.com/zzjcool/krd/issues/7)（「脏矩形」，写于 16×8 tile 时代，
在 per-tile level 与 8×4 tile 之前）。

## 1. #7 当初的主张

当年的实测（16×8 tile），以及合并矩形方案的预测：

| 脏区形态 | 16×8 tile | 合并矩形 | 声称收益 |
|---|---|---|---|
| 一个字符 | 3900 B / 0.50 ms | 82 B / 0.03 ms | 47.6× |
| 一行文字 | 35482 B / 4.04 ms | 6427 B / 0.59 ms | 5.5× |
| 拖 600×400 窗口 | 31912 B / 3.10 ms | 20153 B / 1.90 ms | 1.6× |

## 2. 同样的内容今天多少钱

参考几何（137×44 格、每格 17×33 px = 2329×1452 px，198 块 8×4 tile），`krd --bench --json`：

| 场景 | #7 的主张（16×8） | 今天 8×4 | 今天 16×8 |
|---|---|---|---|
| `char`（一个字符） | 3900 B / 0.50 ms | **332 B payload / 549 B wire**, p50 0.49 ms, **1 tile** | 1017 B / 1462 B, 1.26 ms |
| `line`（一行文字） | 35482 B / 4.04 ms | **1730 B payload / 2864 B wire**, p50 0.91 ms, **6 tiles** | 2618 B / 3777 B, 1.65 ms |
| `full`（整屏） | — | 19047 B / 31362 B, 2.76 ms, 66 tiles | 14463 B / 20928 B, 2.88 ms |

也就是说，这个 issue 立论时那句「改一个格子还要重传 287 KB」，描述的是一个已经不存在的世界。
今天改一个字符在线上只有 **549 B**，一行文字 **2864 B**：比 16×8 时代少 20 倍，
比 #7 用来给自己立论的合并矩形预测（6427 B）还少 **3.7 倍**。tile 尺寸的实验也说明权衡已经平衡：
16×8 会让 `char` 变差 2.6 倍、`full` 好 0.75 倍——而这正是 per-tile level（#3）现在按块做、
而不是全局做的取舍。

真管道复核（`--bench-wire line`，首帧整屏之后的稳态）：每帧 6 块 tile、1731–1735 B payload，与 L1 一致。

> `drag` 故意没进这张表：bench 的 `drag` 用例是噪声内容（和 `photo` 一样），今天的 881 KB 与 #7 的
> 31 KB 不是同一份内容，不构成回归。

## 3. 合并今天还能买到什么（实测）

合并会把 8×4 tile 换成每个脏连续区一条紧贴的矩形。两个实测锚点：

- **每次 placement 的线上开销**：`char` 是 332 B payload 对应 549 B 线上 → 约 217 B 的 base64 + kitty
  逃逸成帧开销；
- **首帧**（`full`，66 块 tile）：2329×1452 px 的 payload 是 19047 B，约每 1000 px 5.6 B。

| 场景 | 今天 | 紧贴合并矩形（估算） | 省下 |
|---|---|---|---|
| `char` | 1 块 tile = 136×132 px 去表达 17×33 px 的变化，549 B 线上，0.49 ms | 线上约 130–250 B（成帧开销就是地板），约 0.2 ms | 约 300–420 B、约 0.3 ms |
| `line` | 6 块 tile = 192 格，2864 B 线上，0.91 ms | 137 格紧贴 = 面积 0.71×，线上约 1.8 KB，约 0.65 ms | 约 1.0 KB、约 0.26 ms |
| `full` / `ui` / `drag` | 脏区本来就连续 | 没有收益：网格已经够紧 | 0 |

换算成预算：打字这类内容剩下的全部机会是 **约 0.3 ms = 50 ms 帧的 0.6 %**，以及 2.9 KB 文本帧里
的约 1 KB。本地 pty 能跑 103.6 MB/s（见 [research-photo-bandwidth](research-photo-bandwidth.zh-CN.md) §0），
哪怕 1 MB/s 的链路每帧也有 50 KB 的额度。这里省下的字节不在任何人的关键路径上——不像 `photo`：
同一份文档量到它每帧 13.58 MB，那里的杠杆是**每像素字节数**（16 位：1.57×），不是矩形形状。

上面标「估算」是故意的：合并改变的是矩形几何，而编码器没有「任意矩形」模式（`--tile 137x1` 最接近，
但它同时改变像素布局，所以不能当代理指标）。

## 4. 为什么代价落在会和设计相撞的那部分

这正是 #7 自己写下的发现，之后也没有改变：自适应矩形需要会移动的 image id 与 placement，而这块协议
工作等于重写渲染器赖以成立的不变量（`ARCHITECTURE.md` §7.1：每块 tile 一个固定 image id + 一个固定
placement id，进程生命周期内不变、永不删除——因为 `a=d,i=<id>` 在 Herdr 和 rex 上会毁掉整个 image
集合，也就是黑屏）。

要发货它，需要：按终端做 placement 寻址删除的探针（#7 §1 的计划）、带 LRU 回收和 VRAM 上限的 id 池、
每 N 帧一次关键帧兜底，还要先回答 #20 那个悬而未决的问题（重新 place 现有 placement 会不会把它排到固
定网格前面）。一天探针加上一次 id 管理重设计，去换 50 ms 帧里的 0.3 ms。

## 5. 建议：关闭

- 字节论据已经落在「不做」那一侧：今天每字符 332 B、每行 1730 B，低于这个 issue 自己主张的合并矩形预测。
- 时间论据是 50 ms 预算里的 0.3 ms（0.6 %），而这类内容现在的 p99 已经是 1.80 ms。
- 实现代价恰好集中在设计承重的地方（id、placement、删除、z-order），那里出错是黑屏，不是慢一帧。

**什么情况下重开**（要证据，不是直觉）：

1. **实测**出某条链路让 2.9 KB 的文本帧成为瓶颈（今天 pty 是 103.6 MB/s，35 倍余量）；
2. 某个终端被证明支持 placement 寻址删除（`a=d,p=<pid>`）——那样 §4 少掉一半，合并矩形才便宜到值得试；
3. #26 的编解码工作落地后，kitty **成帧**成了文本帧的主要成本（今天成帧 217 B 对 332 B payload，
   这确实是天花板——但 549 B/帧不是任何人报过的问题）。
