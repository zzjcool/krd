# 彩色重内容全屏运动：字节花在哪，能做什么

**状态：** 为 [issue #26](https://github.com/zzjcool/krd/issues/26) 做的调研与决策记录。本次 PR 不改编码
管线。下面每个数字都能在 §8 找到命令，或能追到某一行代码。

**English:** [research-photo-bandwidth.md](research-photo-bandwidth.md)

---

## 0. 一页结论

`photo` 用例每帧上线 **13.58 MB**：每像素 3 字节 + 33% 的 base64 + 一层对这份内容**毫无收益**的 zlib
（10.14 MB 原始像素压出 10.15 MB）。20 fps 就是 271 MB/s；本机 pty 上限 103.6 MB/s，所以连本机都只能跑
8 fps。换压缩器救不了——没有可压的东西。只有**每像素更少字节**、**更少像素**、**更少帧**三条路。

参考布局（2329×1452 px、198 tiles）上的实测：

| 方案 | 每帧 wire 字节 | 相对今天 | 画质 | 需要改协议吗 |
|---|---:|---:|---|---|
| 今天：`--format rgb` + zlib + base64 | 13.58 MB | 1.00× | 无损 | — |
| zlib 没收益时跳过 | 13.57 MB | 1.00× | 无损 | 不用（省 137 ms CPU） |
| 18 位色（6-6-6）再 zlib | 10.53 MB | 1.47× | 42.3 dB（肉眼无损） | 不用 |
| **16 位色（5-6-5）再 zlib** | **9.90 MB** | **1.57×** | 36.5 dB（渐变有台阶） | 不用 |
| 15 位（5-5-5） | 9.00 MB | 1.72× | 35.3 dB | 不用 |
| 12 位（3-3-2） | 5.81 MB | 2.67× | 19.9 dB（色块化） | 不用 |
| **采集降到 1/2 分辨率** | **3.41 MB** | **4.56×** | 变软（终端放大） | 不用 |
| 采集降到 1/4 | 0.87 MB | 17.9× | 很软 | 不用 |
| 16 位 **且** 1/2 分辨率 | 2.49 MB | 5.5× | 软 + 台阶 | 不用 |
| 真正在线路上传 RGB565 / YUV 4:2:0 | 5.1–6.8 MB | 2–2.7× | 有损 | **终端得支持新的 `f=`** |
| 帧间差分 | — | — | — | **不可能：终端不会合成** |
| 少发帧（自适应 fps） | 13.58 MB × fps | — | 20 MB/s 链路上是 1.5 fps 幻灯片 | 不用 |

**推荐：** 按 tile 内容自适应的 16 位量化（§4.1），然后是采集侧降分辨率（§4.2），fps 只作为背压而不是
解法。第一条在编码器里大约 40 行，能把一张真实照片从 6.3 MB 降到 1.3 MB（36.5 dB）；第二条机制上已经
现成（zoom 的活已经把采集矩形变成参数），代价是清晰度。两条都不需要新协议、编解码库或终端改动。里程碑
见 §7。

**另外，这个用例的标签本身要改。** bench 里的 `photo` 是哈希噪声——构造上就不可压缩，并**不是**照片
桌面的样子。一张真实的 2329×1452 照片今天只要 **6.32 MB**，16 位下 1.27 MB。259 MB/s 属于最坏情况，
哪个数字该放在哪里见 §3.5。

## 1. 测了什么，用什么测

环境：macOS 26.6.2、M1 Pro、krd @ `d95386d`，参考布局 `--pane 137x44 --cell 17x33 --source 2329x1452`
（198 个 8×4 格 tile，采集 2329×1452 px）。

| 层次 | 命令 | 回答什么 |
|---|---|---|
| L1 编码 | `krd --bench --rounds 8 --json` | 每阶段毫秒、payload 与 wire 字节 |
| L2 线路 | `python3 bench/wire.py --case photo --drain …` | pty（以及限速 pty）实际搬得动多少 |
| 编解码探针 | `python3 probe/photo_codec.py …` | 同一份像素在 §4 各方案下的字节，同一套 framing |

`photo` 的 L1 阶段拆分（并行、198 tiles）：

| 阶段 | p50 ms | 占 24.53 ms |
|---|---:|---:|
| dedupe | 0.00 | — |
| dirty | 0.01 | — |
| extract | 1.20 | 5% |
| zlib | 单线程 136.75 → **墙钟 17.99** | 单核 73%，墙钟 73% |
| base64 | 5.15 | 21% |
| assemble | 1.38 | 6% |
| **合计** | **24.53** | |

两个立刻能得出的结论：base64 不是值得优化的实现细节（5 ms）；zlib 花掉一个核的 137 ms 去掉 0 字节
（§2）。

## 2. 13.58 MB 是怎么算出来的

先算术，再用实测确认：

```
像素          2329 × 1452                    = 3.38 Mpx
原始 RGB      3.38 Mpx × 3 B                 = 10.14 MB        ← 帧本身
zlib          实测 payload                    = 10.15 MB        ← +0.01 MB：压缩器只加了个头
base64        10.15 MB × 4/3                 = 13.53 MB        ← +3.38 MB，纯协议税
framing       198 tiles × 91 B + 分块头       = 0.018 MB        ← 转义、placement、分块头
                                                 13.58 MB  ← 与 `krd --bench --json` 一致
```

实测 `payload`（10,150,xxx 字节）**大于**原始像素，这就是全部故事：这份内容处在最大熵，任何想建模它的
阶段都只能加开销。`bench/budget.json` 从另一侧也这么说——`photo` 的 payload 预算（20 MB）备注是
"content-dominated, so this only catches a format regression"。

字节的实际来源，按大小排：

1. **每像素 3 字节是格式决定的。** `f=24` 就是 RGB888；协议里没有 16 位格式（§3.2）。13.58 MB 里有
   10.14 MB 在一行代码执行之前就决定了。
2. **base64 是 +33%。** APC 转义是文本通道，`o=z` 的载荷同样要 base64（`Sources/krd/Render.swift:278`，
   `o=z` 在 `:290`）。每帧 3.38 MB。
3. **zlib 是 +0.1%。** 在噪声上。在照片上是实打实的 2.2×（10.15 → 4.72 MB），所以它必须留着——但
   该跳过的时候要跳过，见 §3.4。
4. **framing 是 0.13%。** 198 个 placement 和分块头不是问题，写路径的系统调用次数也不是。

## 3. 哪些方案**做不到**，以及原因

这些问题每过一阵就会有人再问一次，所以在这里一次写清。

### 3.1 "用 `f=24` 原始 RGB，不要 base64"

kitty graphics 协议的载荷是 APC 转义里的 base64；`a=t`/`a=T` 没有二进制直传变体（`t=d`/`t=f` 那些
*媒介* 指的是终端去读文件或共享内存，不是客户端发原始字节）。krd 已经在用最小的合法形状：`f=24`
（3 B/px，而不是 `f=32` 的 4）、`o=z`（先压缩再编码）、4096 字符分块。

就算某天终端加了二进制通道，收益是 13.58 → 10.18 MB：**25%**，对 271 MB/s 这件事没有性质改变。不值得
为它扩协议，也不在 krd 的控制范围内。

没有它的实测代价：base64 = 每帧 5.15 ms 与 3.38 MB（§1）。

### 3.2 "线路上直接传 RGB565 / YUV 4:2:0"

`f=` 只接受 24、32、100（PNG）——没有 16 位 RGB，也没有可协商的 YUV。真要 1.5 B/px 上线，需要 kitty、
Ghostty、Herdr/rex 都长出这个格式，**并且** krd 学会用，而且终端合成时还得把它转回 RGB。这是跨终端的
协议改动；哪天该做也应该另开 issue。

今天可做的是：先量化成 16 位，再按 `f=24` 发出去——同样的线路格式，在 zlib 之前先删掉低位的熵。这就是
§4.1，拿到了 16 位格式的大部分收益，却没有它的部署成本。

### 3.3 "帧间差分 / 在同一个 image id 上覆盖"

终端是个哑接收方：对一个 placement，只有"这是像素"和"删掉"两种操作，它不做任何合成。所以"差分"
不是更小的载荷，而是**渲染不出来**的载荷——除非 krd 自己把绝对帧重建出来再发，而那正是它已经在做的事。

`a=f`（kitty 的动画帧）也没用：帧是一次性全量传过去的，那是预付，不是压缩。

"差分"里**已经实现**的部分本来就在管线里：完全相同的帧不发（`Capturer` 丢掉逐字节相同的帧），tile 级
的脏判定在 `Tile.swift`。所以打字只要 0.3 KB、静止画面 0 字节——而当每个 tile 的每个像素都在变时（这个
用例的定义），它一点也省不下来。

### 3.4 "换个更好的压缩器"

实测：zlib level 1、6、9 在这份内容上都是 10.15 MB（探针里 `zlib1/zlib6/zlib9` 三行字节完全一致）。
brotli/zstd/libdeflate 也只会得到 ~10.15 MB：熵就是熵。`#8`（用 Rust 重写编解码）是**速度**项目，而
速度在这里不是瓶颈——一帧 24.53 ms 的单核时间，对应 100 ms 的写时间。

这条轴上唯一值得做的是反面：**没收益时别压**。试一次 zlib，只有比"原始字节 + 头"更小才采用；在
`photo` 用例上每帧省 137 ms 单核时间（编码时间的 73%）和 0.01 MB。便宜、无损、不牵涉协议——很好的 M1
（§7）。

### 3.5 "bench 那个数字就是照片"

它不是。`BenchContent.noise`（`Sources/krd/Bench.swift:140-147`）是逐像素整数哈希：它代表最坏情况，
不代表照片。用一张真实的 2329×1452 照片（`/System/Library/Desktop Pictures/Sonoma.heic`，用 `sips`
转换，见 §8）实测：

| 内容 | 原始 | 今天的 wire | zlib 压缩比 |
|---|---:|---:|---:|
| 哈希噪声（bench 的 `photo`） | 10.14 MB | 13.58 MB | 1.00× |
| 真实照片 | 10.14 MB | 6.32 MB | 2.15× |
| 平滑渐变 | 10.14 MB | 0.05 MB | ~200× |

也就是说：271 MB/s 是**最坏**桌面的天花板；视频或修图桌面今天在 20 fps 下是 126 MB/s。两个数字对远程
链路都太大，但"照片类应用"的规划数字是后者；而预算（§6）必须按前者守住，因为 bench 生成的就是前者。
一个行为像照片的合成 `photo` 用例（平滑底 + 颗粒，约 2× 可压缩）会让 bench 更有代表性——那属于 bench
改动，作为后续 issue，不塞进这份文档。

## 4. 能做的，都带实测

下表全部来自 `probe/photo_codec.py`，同一份像素、同一套 kitty framing，因此可以直接和 `krd --bench`
对比。`wire` 含 base64 与每 tile 91 B 的 framing；`psnr` 是相对未量化帧（每 32 行采样，
`probe/photo_codec.py:psnr`）。

### 4.1 更便宜的像素：zlib 之前先量化（不改协议）

| 变体 | 噪声：wire | 相对今天 | 照片：wire | 相对今天 | PSNR（照片） |
|---|---:|---:|---:|---:|---:|
| 今天（`f=24`、zlib 6） | 13.58 MB | 1.00× | 6.32 MB | 1.00× | 无损 |
| 6-6-6（18 位） | 10.53 MB | 1.47× | 2.98 MB | 2.12× | 42.3 dB |
| 5-6-5（16 位） | 9.90 MB | 1.57× | **1.27 MB** | **4.98×** | 36.5 dB |
| 5-5-5（15 位） | 9.00 MB | 1.72× | 0.98 MB | 6.45× | 35.3 dB |
| 3-3-2（12 位） | 5.81 MB | 2.67× | 0.26 MB | 24× | 19.0 dB |

顺带一提：`--format rgba` 在噪声上贵 14%、在照片上贵 5%（zlib 把恒定的 alpha 平面吃掉了），这也是
`f=24` 是默认值的原因。

为什么量化能赢过"更好的压缩器"：它不试图预测噪声，而是**删掉**噪声。照片的熵就藏在低位，丢掉低位会让
平滑区域变成 LZ77 终于能匹配的长串——2.15× 的 zlib 变成 8×（照片：4.72 MB payload → 5-6-5 下
0.94 MB）。

画质：42.3 dB 是真的看不见；36.5 dB 属于"照片看着没问题、平滑天空渐变能看出台阶"；19 dB 是 1990 年代的
GIF。纯色 UI 在 5-6-5 下基本不变（每通道最多偏 4/255，而纯色块正是最不显眼的地方），文字的对比度还在，
照片和渐变会出现台阶。所以它必须**按 tile、按需**启用，而不是全局格式开关：Finder 窗口和一帧视频是
两类客户。

代价：多一遍量化（探针里是 `bytes.translate`，Swift 里大约 13 行 + 一张 256 字节表），如果两种都试就是
两遍 zlib。更好的设计是：每个 tile 记住上一帧的压缩比，连续两帧不可压（> 1.05）就从下一帧起按 5-6-5
发，直到它重新变得可压——第二遍只发生在真正有噪声的 tile 上。

### 4.2 更少的像素：采集降到 1/2 或 1/4

采集矩形和输出尺寸本来就已经是参数（`SCStreamConfiguration.width/height`，zoom 的活已经会算这两个），
所以"按半分辨率采集、让终端把 placement 放大"是工作量很小、又完全不碰协议的一条路。

| 变体 | 噪声：wire | 相对今天 | 照片：wire | 相对今天 |
|---|---:|---:|---:|---:|
| 今天（全分辨率） | 13.58 MB | 1.00× | 6.32 MB | 1.00× |
| 1/2 分辨率（1164×726 px） | 3.41 MB | 4.56× | 1.48 MB | 4.27× |
| 1/4 分辨率（582×363 px） | 0.87 MB | 17.9× | 0.41 MB | 15.4× |

它和 §4.1 可以叠加（1/2 分辨率 + 5-6-5 = 噪声 2.49 MB）。画质代价就是变软——而这正是 zoom issue（#22）
反方向做过的同一个权衡，用户已经懂。

### 4.3 更少的帧：线路到底搬得动多少

`bench/wire.py`、`photo` 用例、三档 drain（数字是 pty 端到端实测）：

| drain | 送出的帧 | 实际 fps | write p50 |
|---|---:|---:|---:|
| 不限速（pty 能多快多快） | 12.50 s 内 100 帧 | 8.0 | 90 ms |
| 20 MB/s | 64.7 s 内 100 帧 | **1.55** | 618 ms |
| 5 MB/s | （算术：13.58 MB/帧） | 0.37 | — |

两次实测的 `late` 都是 **100/100**：krd 不会无限排队，它只是写得很慢，于是流一路落后。20 MB/s 的链路
就把彩色全屏运动变成 1.5 fps——当幻灯片能看，当视频不能。这就是方案 C 的诚实代价，也是为什么 C 单独
不是答案：在 16 位 + 1/2 分辨率下，同一条链路能跑 15 fps。

## 5. 落地后 bench 会打印什么

如果某个方案落地，`krd --bench` 会报出（按 §4 的字节推算，同一套阶段模型）：

| 场景 | payload | wire | 编码 p50（墙钟） |
|---|---:|---:|---:|
| 今天 | 10.15 MB | 13.58 MB | 24.5 ms |
| zlib 没收益时跳过 | 10.15 MB | 13.57 MB | **6.5 ms**（不跑 zlib） |
| 5-6-5 + zlib | 7.40 MB | 9.90 MB | ~42 ms（两遍 zlib；用"记住 tile"则是 24 ms） |
| 5-6-5 + 1/2 分辨率 + zlib | 1.85 MB | 2.49 MB | ~11 ms |

两遍量化会让编码时间**变大**，跳 zlib 会让它**变小**；两者都不是重点。重点是 13.58 → 2.49 MB，这是
"不能用"和"局域网上能用"的差别。

## 6. 这个 PR 实际改了什么（不改编码器）

- `docs/research-photo-bandwidth.md` + `.zh-CN.md`（本文档）。
- `probe/photo_codec.py`：测量工具，只用标准库。
- `bench/budget.json`：给 `photo` 加一条 **`bytes.wire`** 预算，取值是今天的数字（13.6 MB）。注意它
  不是"设计上就是要失败"的那种：#31 刚让这道 CI 门禁变得有意义，一条注定红的检查会正好毁掉它。一条
  只会往下走的**上限**才是能在团队里活下来的版本。
- `README.md` / `README.zh-CN.md`：**粗糙** 那行改成指向数字所在的地方，而不是暗示有个神秘编解码器。

## 7. 推荐路线与里程碑

**推荐 B（更便宜的像素）+ 内容自适应，然后 A——而 A 实际上等于"更少的像素"。** 不是视频编解码器，不是
协议扩展。

- **M1 — 先停止做无用功（一天）。** 逐 tile：zlib 结果不比输入 + 头更小就发原始字节。这份内容上省掉
  73% 的编码 CPU，文字路径零代价。顺便把 bench 改成诚实地区分"最坏情况"（再加一个带照片统计特性的
  用例）。
- **M2 — 内容自适应 16 位（几天）。** 逐 tile 记住上一帧的压缩比；连续两帧不可压（> 1.05）就从下一帧
  起按 5-6-5 发，直到它重新可压。常见场景不需要任何开关，想要无损的人用 `--format` 那一类覆盖。预期：
  最坏情况 13.58 → 9.90 MB，真实照片 6.32 → 1.27 MB，文字路径逐字节不变。
- **M3 — 采集降分辨率（几天）。** 采集侧 `--scale 1|0.5|0.25`，然后一条简单策略："管道跟不上时先降
  分辨率，再降 fps"。和 M2 叠加。
- **M4 — 只有终端愿意配合时才做。** 16 位或 YUV 的线路格式。需要 kitty/Ghostty/Herdr 一起改；不要在
  krd 里先开工。

**不做：** 运动补偿、内置视频编解码器、线路上的 YUV、协议扩展、负责重编码的 daemon，以及任何破坏"单
进程、无状态 tile、终端只是哑图片接收方"模型的东西。这些是纸面上很香、实际上会让项目变形的东西。

## 8. 每个数字，以及怎么复现

```bash
# 布局、阶段拆分、payload/wire 字节（§1、§2）
swift build -c release
./.build/release/krd --bench --rounds 8 --pane 137x44 --cell 17x33 --source 2329x1452 --json

# 管道上限与 20 MB/s 的现实（§4.3）
python3 bench/wire.py --case photo --seconds 3 --drain 0  -- ./.build/release/krd --bench-wire photo --pane 137x44 --cell 17x33 --source 2329x1452
python3 bench/wire.py --case photo --seconds 3 --drain 20MB -- ./.build/release/krd --bench-wire photo --pane 137x44 --cell 17x33 --source 2329x1452

# 编解码表（§4.1、§4.2）
python3 probe/photo_codec.py --content noise
python3 probe/photo_codec.py --content gradient
sips -Z 2329 -s format bmp "/System/Library/Desktop Pictures/Sonoma.heic" --out /tmp/sonoma_full.bmp
sips -c 1452 2329 /tmp/sonoma_full.bmp --out /tmp/sonoma.bmp
python3 probe/photo_codec.py --bmp /tmp/sonoma.bmp
python3 probe/photo_codec.py --bmp /tmp/sonoma.bmp --scale 2
```

交叉验证：`probe/photo_codec.py --content noise` 的基线行给出 10.15 MB payload 与 13.58 MB wire，与
`krd --bench --json` 对 `photo` 的报数完全一致。也就是说探针的 framing 模型
（`Sources/krd/Render.swift:277-302`）与真实实现对齐到三位有效数字——这才是它其它行值得读的理由。
