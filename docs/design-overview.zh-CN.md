# 落地屏：三块屏与最近用过的三个窗口

[English](design-overview.md) | 简体中文

**状态：** v8 · 样机 [docs/media/overview-mockup.html](media/overview-mockup.html)
（`#wins=7&others=1` 默认 · `#start=4` 滚到末尾 · `#wins=14&others=2&per=4` 很多窗口 · `#fail=1` 拍不到时的样子）。

## 1. 一眼看去

```
▪ krd    7 个窗口 · 3 块屏 · 最近使用在前                       ╷
┌────────────────────────────────────────────────────────┐   ▲
│                                                        │   █
│             主屏：按原比例铺到舞台里，余量透明             │
│                                                        │   │
└────────────────────────────────────────────────────────┘   ▼
🖥 内建显示器 — 1512×982 · 主屏 · 1/3                        ╵
────────────────────────────────────────────────────────    
▣ 最近使用    1–3 / 7                                ⤢ 3   ╷
┌──────────────┬──────────────┬──────────────┐             ▲
│    Safari    │    Xcode     │   Terminal   │             │
└──────────────┴──────────────┴──────────────┘             ▼
▣ Safari — Apple…  ▣ Xcode — kkrt…  ▣ Terminal — ~/code…
▪ 点卡片进入 · 右边竖条上下滚 · 静止后 0 B/s        4 块图 · ~28 KB
```

- **上**：舞台。**一次只放一块屏，按原比例 fit 进舞台**（余量透明，露出墙自己的底色）；其余屏靠右边竖条往下滚。
- **下**：`最近使用` 的三个窗口卡片；同样用右边竖条滚，`⤢` 切换一屏 2 / 3 / 4 个。
- **右边缘**：一根**与屏幕等高的竖条**，分成两段——上段配给显示器，下段配给窗口。
  顶端 `▲`、底端 `▼`、中间滑块 `█`；点空白格按位置跳过去。**没有 `◀ ▶` 这种小三角了。**
- 每块图下面一行说明（`🖥 名字 — 分辨率`、`▣ App — 标题`）；点图或点说明都进入。
- 进入后底部一行 `⬅ 🖥 返回`。**没有快捷键**：按键全归远程桌面，`Ctrl-\` 仍是唯一例外。

## 2. 为什么是三个

- 终端里一块能看清的卡片至少 24–44 格宽；137 格的面板放 3 张正好，4 张标题就开始被截。
- 有"最近使用"排序，想进的那个基本在第一页；滚动只是兜底，不是主路径。
- **屏一次只放一块**（理由见 §6.6）：屏的数量不该影响成本，也不该让每块屏都缩成一条。
- 于是采集数 = 1 块屏 + 可见的 3 个窗口 = **4 次**，≈28 KB；窗口堆到 20 个、屏堆到 5 块，这个数字都不变。

## 3. 顺序从哪来（实测）

在真机上跑 `CGWindowListCopyWindowInfo(.optionOnScreenOnly, .excludeDesktopElements)`：

```
  5  layer 0  pid 67529  Rex Beta       Settings - Developer          103x112
  7  layer 0  pid 93439  WindowManager  Gesture Blocking Overlay      149x155
  8  layer 0  pid 26465  WeChat         Weixin                        149x155
 22  layer 0  pid 40544  Brave Browser  2026年度暗黑佳作…              1452x1050
```

- 它返回的就是**前到后的 z 序**，等价于"最近被抬到最前"。Windows 的"最近使用"用的是同一套。
- **坑**：系统会插入 `WindowManager Gesture Blocking Overlay`，它**也是 layer 0**，还和真窗口成对出现。
  所以过滤条件只能是"**拥有者是 regular app（有 Dock 图标）**"，按 layer 或尺寸筛都会漏。
- **不是严格 MRU**：窗口被抬起但没激活也会前移。免费的近似，够用。
- 严格 MRU 要自己记账，而 `NSWorkspace.didActivateApplicationNotification` 在 krd 里**收不到**——
  krd 不跑 NSApp 的 run loop（见 `ARCHITECTURE.md` 里屏幕参数通知那段）。要真做得起一个只跑
  CFRunLoop 的后台线程，代价和收益不成比例。
- 顺序、拥有者、尺寸、PID **都不要屏幕录制权限**；**只有标题要**。没权限时卡片第二行退化成"第 N 个窗口"。

## 4. 图，还是遮罩

**默认就是图。** 遮罩不是"省资源的默认态"，而是**拍不到时的兜底**（窗口刚被关、权限被拒、pixel buffer 拿不到）：

- 遮罩和图的**矩形完全相同**（同样是这块格子），所以"拍到 → 遮罩"或反过来都不会让版式跳一下。
- 遮罩上画 `👁 名字 / W×H 格`，点它跟点图一样进入。
- 遮罩会**说明原因**，一个词，就写在图该在的位置：`closed`（窗口没了）、`denied`（屏幕录制权限）、
  `no stream`（窗口服务器拒绝这个窗口，`-3805`）、`no pixels`、`failed`。所有原因画的都是同一个矩形，
  没有这个词，读者能报告的只有"没有图"——而"没有图"是问题，不是答案（`PanelCaptureError.maskLabel`）。
- 一屏只有 3 个窗口，所以"默认全开"的总量被**结构**限制住了，不需要靠"默认不放图"来省。

## 5. 交互

| 输入 | 动作 |
|---|---|
| 点窗口卡片（或它下面那行字） | 进入那个窗口（单窗口镜像，20 fps） |
| 点舞台上的屏 | 整屏镜像 |
| 点竖条上段的 `▲` / `▼` | 上一块 / 下一块屏 |
| 点竖条下段的 `▲` / `▼` | 上一组 / 下一组窗口（一组 = 一屏 3 个） |
| 点竖条中间的 `│` | 按位置跳（滑块 `█` 标出当前位置） |
| 点 `⤢` | 一屏显示 2 → 3 → 4 个窗口 |
| 点 `⬅ 🖥 返回` | 回到落地屏 |
| 任何按键 | 原样转给远程桌面 |

到头的那一端画成暗色并且不响应——不会有一堆"点了没反应"的死格。

## 6. 右边那根竖条

好用的滚动控件在终端里只有一种形态：**大、贴边、位置固定**。

- **一格宽，和面板一样高**，贴右边缘；内容宽度永远让出这 2 格（竖条 + 1 格留白）。
- **两段**：上段覆盖舞台的高度，下段覆盖卡片的高度，中间用 `╵`/`╷` 断开。
  位置固定，所以"滚窗口"永远是同一个地方，不用先找。
- **段内**：`▲` 顶格、`▼` 底格、中间 `│` + 一个 `█` 滑块；滑块位置 = 当前位置/总长度。
- 点 `│` 按比例跳；点 `▲`/`▼` 走一格（`滚动=一页` 时走一屏）。
- 只有 1 块屏 / 窗口不满一屏时，整段变成一条连续的暗色 `│`，**不画灰色箭头**——一个点了没反应的箭头
  是在撒谎，说"这里能按"。滚不动就不该有形似可点的东西（`WallCanvas.drawSegment` 就是这么写的）。
- **竖条绝不碰最后一行的最后一格**：那一格写下去会武装 pending-wrap，下一个字节就滚屏，整面图错一行
  （`Chrome.swift:459-463` 就是为此；而且只改那一格的差异会被整段丢掉，`:464`）。所以下段的 `▼` 停在
  页脚上一行，页脚那一行不属于任何段。

为什么不是 `◀ ▶`：它们在终端里只有 1 格宽 1 格高，鼠标点上去要好几次才中；竖条有 20+ 格高，
而且滑块顺带把"我在这堆里的哪个位置"说清楚了。

## 6.5 版式（行预算怎么分）

从上到下：表头 1 行 → 舞台（`舞台高 + 1` 行说明）→ **分隔线 1 行** → 卡片带表头 1 行 → 卡片（`卡片高 + 1` 行说明）→ 空 1 行 → 页脚 1 行。

分隔线是评审加的：没有它，舞台说明、卡片带表头、卡片顶边是三条紧贴的行（"太密集了"）。用一条暗色 `─` 比空一行便宜——它说明"这一段结束了"，空一行什么都不说。它也是**第一个被砍的东西**：`rows < 20` 时不画（`dividerRow` 为空矩形），短面板里一行规则不值一行图。

**上面桌面 7，下面窗口 3。** `舞台高 = round(0.7 × 预算)`，卡片带拿 `预算 - 舞台高 - 1`（那 1 是卡片带自己的说明行），其中 `预算 = rows - 6`，短到没有分隔线时是 `rows - 5`。撑不到 `minCardRows` 的卡片带直接丢掉，行给舞台，而不是留一条两行的残带。这之前是卡片先按理想高度拿走，舞台捡剩下的：240×44 下卡片 23 行、舞台 14 行，桌面就变成"空墙中间一张小图"（用户原话「桌面缩在一角，其余全黑」）。分配之后**比例仍然会再压一次**：更高的面板会把 16:10 用不掉的行还给卡片，卡片趁机变宽（137×73 是 42 + 24）。

- **一页的卡片按"这一页有几张"分宽度，而不是按 `per`。** `per` 只是"最多能放几张"的上限，所以
  `pageCount < per` 的页（最后一页，或者本来就没那么多窗口）里，每张卡宽
  `floor((content - (pageCount-1) × gap) / pageCount)`，而不是一个 `per` 宽的槽位。以前只有一个窗口时，
  卡片只占卡片带的三分之一，另外三分之二全是墙：图贴在最左边、右边 80 格空白，看起来像"卡片放错位置"，
  而不是"这一带只有一张卡"。现在卡片框就是整条带子，里面的图保持自己的比例并居中（137×44 下单个 16:9
  窗口左右留白相等），说明行也跟着**图**走——挂在框的左边缘就成了给空白打的标签。
- 内容宽度 `content = cols - 2`（竖条 + 留白）；卡片宽 `winW = floor((content - (per-1)) / per)`，
  137 列 / 3 个 → 43 格。卡片带的**高度**来自 7:3 的分配（137×44 下 10 行），所以卡片是个"框"而不是一个固定形状：里面的图保持自己的比例，通常在这里是宽度受限。`idealCardH = winW / (1.62 × cellAspect)` 是"高面板"才够得着的高度，到那时候卡片已经变宽（每页更少），图跟着框一起长大。
- 卡片之间：`cardGap = max(1, content / 45)` 格——137 列下 3 格，60 列下 1 格。最初是 1 格，评审觉得
  像是"贴在一起"；间距跟着宽度缩放，因为窄面板上的留白是拿卡片换的（60 列时间距 3 格会让 `per` 从 4 掉到 3）。
  137 列下 3 格间距的代价是卡片少一行（44×14 → 43×13），那一行给了舞台（23 → 24）。
- 舞台说明行永远紧贴画面下一行；画面放不进内容区宽度时**必须居中**（`PanelImage.fit` 的 `cellRect` 已经是居中的那个矩形，`emitPanel` 把光标移到它的左列再贴图）。实测（真实 cell 16×33）：240×44 → 89×27 格、左起第 75 列（两侧各留 74/75 列，占宽 37%）；200×50 → 102×31、左起第 49 列；137×73 → 135×41，满宽。宽而矮的面板在"不裁不拉伸"下**不可能**满宽（面板比例 2.64 vs 桌面 1.6），居中是这个前提下唯一诚实的结果。
- 全部按**整格**落位；永不写最后一行的最后一格（autowrap 会把整面图顶走）。
- 所有截断与对齐走 `DisplayWidth`（CJK、emoji 是双宽）。`⤢ ▣ ▲ ▼ ⬅ ╷ ╵` 属 East-Asian-Ambiguous，
  所以有 `--symbols ascii`（`> w ^ v < . '`）兜底，两套必须排出同样的列数。
- **实测纠正**：`🖥`（U+1F5A5，没有 VS16）在 `TextWidth.swift` 的表里是 **1 格**，不是 2 格——它没有默认
  emoji 呈现，终端一般也按 1 格画。设计稿早先把它当成双宽，是错的。

## 6.6 屏和窗怎么放进格子

**一律 fit：保比例，不裁、不拉伸。** 画面按自己的宽高比缩到带子里能放下的最大尺寸，**而"面板"就是那张画面本身**：图就是拟合出来的像素，放在拟合算出的那些格子上，带子里剩下的格子**干脆不画**——露出来的是墙自己的背景，所以卡片看起来是一扇浮在墙上的窗，不是一个相框。

| 情况 | 处理 |
|---|---|
| 横向屏（16:10 / 1.54） | 宽度贴满舞台的列，高度由比例决定（137×73 的窗格在 8×16 的 cell 下是 53 行带子里的 42 行），带子里剩下的行就是墙 |
| 格子从哪里来 | 一份 `PaneGeometry` 快照：pty 有 `ws_xpixel` 就用它，否则用终端自己的 `CSI 16t`/`14t`，再不行用 8×16 兜底（8×20 是 CRT 时代的格子，它的 2.5 宽高比对上真实的 2.0 会让舞台空出 36%）。启动测一次，每次 resize 重测（`PaneGeometry.measure`） |
| 竖向屏（1200×1920） | 仍是高度受限，只是那条画面窄（约 29 格），居中 |
| 窗口卡片 | 卡片矩形**永远不变**（设计尺寸 43×13 格），画面按窗口自己的比例缩进去，余量透明；窗口 980×620 几乎不留边，760×900 就在两侧留空 |
| 角 | **圆角**，短边的四十分之一（`--square` 改回直角）。第一版是直角（"把圆角边框去掉吧"），因为切角就是图上的洞、洞会被终端自己的底色填上，圆角图看起来像"框套一张小图"。那个"框"是另一个 bug：ScreenCaptureKit **不会放大，会填黑**（`PanelCapture.fitted`），于是图的像素里其实是"桌面缩在一角 + 一圈黑"。现在图严格等于它的格子，角上的洞在图的内部、露出来的是图躺着的墙面，正是窗口该有的样子。这是墙面图里唯一的 alpha；镜像的 tile 仍然是不透明 RGB |
| 像素只是清晰度，格子才是几何 | 用 unicode placeholder 时终端把图装进图片的格子里（§6.9），所以抓图按"每格 `pane.dpr` 个设备像素"——用点上报的终端取 2、用设备像素上报的取 1，`--dpr N` 可覆盖（两轴同乘，单边上限 4096 px）。像素路径（`--no-placeholders`）没有这层"装"，图 *必须* 按设备像素要——而用点上报格子的终端根本给不出这个数，所以那条路要 `--cell`，也因此占位符才是默认 |
| 一行一个高度 | 一页里的卡片**画在同一高度**：所有画面在不裁不拉伸的前提下都能达到的最高高度，也就是最宽那个窗口的高度（`WallPanels.sharedCardHeight` + `PanelImage.fit(maxHeight:)`）。按窗口各自 fit 会让 16:9 的卡片比正方形的矮一截，一行上下沿参差不齐（评审：「窗口的最高高度需要保持一致」）。代价是这一页里有个超宽窗口时同排跟着变矮；另一个选择是裁切，设计里明确排除 |
| 算 fit 的公式 | 只有一个方向，**格子 → 像素**：`availW = cols×cellW`、`availH = rows×cellH`；若 `availW/availH > aspect` 则高度是约束，否则宽度是约束；结果取整成**整格**（`PanelImage.fit`），图的像素随后就正好是"格子 × 格子尺寸"（`86×27 格 × 8×16 = 688×432 px`，一个像素都不多），面板内没有偏移。反过来做——先在像素里 fit、再取整回格子——会让图比盒子最多大半格：1:1 画的终端上是一个缺口，会缩放的终端上则被藏成 1~2% 的拉伸 |
| 顺序 | 菜单栏那块第一（`kCGDisplayIsMain`），其余按 `bounds.origin.x` 从左到右 |
| 采集 | **一次只拍台上那 1 块**：3 块屏 + 3 窗 = 4 块图，和只有一块屏时一样省 |

为什么不 cover：cover 会裁掉内容，而"屏幕的实际比例"本身就是信息——菜单栏没了、Dock 没了，用户第一眼就认不出这是哪块屏。fit 多花的代价只是留边，而留边透明之后，那圈边根本不是"墙上的装饰"，而是墙面本身。

为什么图里根本不该有留边（三版都实测过）：黑边像给每张图套了个相框；"画面最外侧那圈的主色"仍然是在猜墙的颜色（浅色窗配浅色边，放在深色墙上就是一条亮带）；而透明留边（`f=32`，alpha=0）只在"终端把 alpha 混到**格子背景**上"时才看不见——**Rex 把透明图片像素直接画成黑色**，于是"画面只占画布 64%"的舞台到手就是"一张图外面套了一圈黑"，用户报成"画面比框小、是不是采集分辨率错了"。分辨率没错：像素就是拟合出来的尺寸。修法是**根本不再发画布**：图就是画面，位置就是拟合出的格子，画面和带子之间那些格子不画——这正是镜像一直在做的（它的留边格子从来不画），也没人觉得那是 bug。

**带子就是画面，永远不是一个"装着画面的框"。** 高大的面板里，行预算原先给舞台的行数超过 16:10 画面需要的（137×73 时 53 行 vs 42 行），而说明行又贴着画面下面一行，于是那段余量以墙面的形式出现在**画面和分隔线之间**——就在黑框修好之后，用户随即报的是"显示屏比它的框小"。现在 `WallLayout.make(stageAspect:cellAspect:)` 按画面算舞台带的高度，用不上的行给卡片带，而卡片带用**更少、更宽的卡片**把这些行吃掉（`per` 是上限）：137×73 下从三张 43×13（图 344×218）变成两张 66×22（图 528×357），整个墙上没有一处带子余量。它**从不**为了填满带子去拉伸画面——被拉扁的桌面比留边的桌面更假，而比例是这面墙唯一确定知道的事。

图片所在的那块格子仍然要先清空：占位框和旧图就住在同一批格子里。`WallCanvas` 的 `.picture` 分支会把画面矩形写成空格（只写空格、不写可见字符，仍然守 `Chrome.swift:11-14`），清完再把图放上去。

不让窗口比例改写卡片矩形的理由：**版式固定**是这张落地屏的全部价值——卡片大小随窗口大小变，点第二次就点不中了。

## 6.7 画面居中（镜像）

**画面块在给它的那块区域里居中，而不是钉在左上角。** 窗口自己的像素比面板少（137×44 的面板里放一个 98×111 的小窗），
或者屏幕的比例比面板更高，以前余量全堆在右边和下边。那看起来像渲染 bug，不像留白——眼睛第一步就看画框，
一边没边就直接判定不对（评审：「不管是窗口还是桌面，这里应该需要居中」）。

| | |
|---|---|
| 区域 | 面板减去镜像自己的顶栏（1 行，§6.8）、减去 `--dev` 的状态行和面板行；画面按 §6.6 的规则 fit 进剩下的部分，再在其中居中 |
| 奇数余量 | 多出来的一行/一列给右边和下边，和所有版式的取整方向一致 |
| 余下的格子 | 属于终端自己的背景：镜像不去画它，会话开始时的 `ESC[2J` 已经清过。改尺寸会再清一次（`handleResize` → `writer.clear()`），所以缩小之后不会留残影 |
| 鼠标 | 同一个原点要在**两个方向**上都减掉：`Viewport.originCol/originRow` 给 SGR 单元格，`originPixelX/Y` 给 SGR-Pixels。不减的话每次点击都会落在手指左上几格 |
| 代码 | `TileGrid.make(area:)` → `originRow/originCol`，被 `rect()`（也就是瓦片的放置位置）和 `--full-frame` 的单张图共用 |

墙不受影响：它的面板由 `WallLayout` 用各自的矩形摆放，所以墙从来没有这个 bug。

## 6.8 镜像戴一条顶栏

**由墙交接过来的**镜像（`--wall-at`）顶部多一行 macOS 窗口装饰：

```
 ●  ●  ●   Terminal — admin — scroll.sh            18 fps  ·  1.8 MB/s  20:07:17  [ - ]
```

* 整行反显，读起来是"家具"而不是画面；
* 标题是窗口的 app 和标题，或者 `display 1 · 1440×2560`；
* `[ - ]`（以及三个圆点，红灯干的就是这件事）**把这个窗口缩回墙里**，回到点它时那一页。走的是和 `Ctrl-\` 同一条路：
  `shutdown()` → 带 `--wall-at` `exec` 回墙；
* 窄面板先丢码率和时钟，**按钮永远不丢**——没有按钮的顶栏是假装成控件的装饰；
* 默认只给"交接过来的"镜像戴；手打的 `krd --window <查询>` 保持裸装（它不是从货架上来的，凭空多一条状态栏要解释），
  `--bar` / `--no-bar` 两种都能覆盖。

它不是 `--dev` 那条线：那条是测量（`pipe 54 ms`），住在底部。两者可以同时开，顶栏只花掉画面一行。

## 6.9 图的位置由格子决定，而不是由像素决定

**终端把图"装进"这块格子**。墙上的图片走 kitty 的 *unicode placeholder*（`U=1`）：一次传输（`a=t`，不带放置）、
一次虚拟放置（`a=p,U=1,c=…,r=…`，就是图片自己的格子矩形）、再加一整片不可见的 `U+10EEEE` 格子——矩形里每格一个，
图像 id 放在前景色里，每行第一个格子带一个组合变音符，其余格子按"左边格 + 列 1"继承。

为什么要换掉按像素尺寸的放置：`c`/`r` 加一张图，等于请终端去 *缩放*，而终端完全可能用点来回答 `CSI 16t`、却按
一图素一设备像素来画。于是"按盒子尺寸做的图"到了屏幕上只有盒子一半宽、贴在左上角，同一个盒子的其余部分是终端
自己的背景——这正是本节存在的原因（`外面是全宽了，桌面还是靠左`）。用 `U=1`，图会被"fit 进指定的矩形，保持宽高比"
（kitty §Unicode placeholders）：这块格子矩形就是布局自己算出来的，不需要任何估计。

| | |
|---|---|
| 格子 | `WallPanels` 的 `fit.cellRect`——和 `WallLayout` 给图片的整流是同一个，也是字幕格的父格（§6.6） |
| 像素 | **只决定清晰度**。用占位符时按"每格一个上报像素"抓图（`--dpr` 可覆盖）；按大 pane 的设备分辨率抓，会撞上终端的图片大小上限，而被拒的图过去看起来正是"图变小了" |
| 像素路径 | `--no-placeholders`。这条路上图 *必须* 按设备像素抓，所以终端用点回答时 `PaneGeometry.dpr` 取 2 |
| 探测 | 启动时一次：1×1 的图用 `q=2` 静默传输、用 `q=0` 做占位符放置。回 `OK` 走占位符；回 `E…` 或不回，走像素路径。日志里有一行写明结果——因为不支持 `U=1` 的终端会把占位符格画成缺字方框，铺满整块图区 |
| 单一快照 | `PaneGeometry`（网格、格子、dpr、来源）只在启动和每次 resize 时测量一次。布局、每个抓图尺寸、鼠标映射全部读它；别处不许再测终端 |
| 镜像也一样 | 镜像的 tile 走同一条路（`emitTileAsPlaceholder`）：一次传输、一次落在 tile 格子上的虚拟放置、一片盖住这些格子的占位符网格——于是操作页和预览页是**一条通道**，`--scale` / `--quality` 也终于只表示*清晰度*，而不是能让图移动的旋钮。VM 上 100×30、同一段 2.6 s 流实测：占位符 113 个 tile = 704 KB，像素放置 96 个 tile = 612 KB——网格开销约 2~4%，而且只重写脏 tile。`--bench` / `--selftest` 仍走像素放置，因为它们的数字是字节契约 |
| 帧就是格子的那块像素 | 镜像的帧是 `cols × cellW` 乘 `rows × cellH`（再乘 `--scale`），绝不是源自己的像素数。按"一图素一设备像素"画的终端，没法把一个便宜几百分之几的帧拉进便宜几百分之几的格子：差额会变成**每一行 tile 之间的一条缝**——实测是 117×38 格的操作页上九条黑线（1920×1200 的帧压在 2006×1254 的格子上，TROUBLESHOOTING 23g）。每块 **tile** 的矩形同样是格子那块像素，算的是同一套式子：按比例切帧只在"帧正好等于 `cols × cellW`" 时才对，其余情况差一个取整；`make(fillsCells:)` 让占位符路径直接要"格子本身"，所以占位符帧永远不会比它画的那些格子小 |
| 两条通道，两条像素规则 | **流**（`SCStream`）要得比源的像素多，它会**上采样**（1920×1200 的屏，请求 2006×1254，交付就是 2006×1254，不丢帧），所以镜像按格子的像素要。**截图**（`SCScreenshotManager`）要得多了会用**黑边填充**，所以墙上限就是源的尺寸（`PanelCapture.fitted`），再自己精确放大一次（`PanelRaster`）。别把一条规则搬到另一条上 |
| `--scale` 自己挑传输路径 | 占位符网格按"一图素一设备像素"画，没法把一个**更小**的帧拉回图片的格子里；而**像素放置**（`a=p` 配 `c`/`r`）是终端自己缩放的——这才是 `--scale` 一直以来的前提。所以：在"格子按设备像素上报"的终端上，`--scale < 1` 会切到像素放置并打一行日志。Rex 上实测 0.8：占位符路径把画面切成 15×10 块、每块只占自己格子的 80%（14 条竖缝 + 9 条横缝，评审语「画面被割裂」）；像素路径把同样的格子铺满、略软，30 KB/s 对满 scale 的 111 KB/s。`--scale auto` 在占位符开启时永不降档：那时光掉的是帧率和颜色，不是分辨率。所以能留在占位符路径上的帧，永远不会比它的格子小：`--placeholders --scale 0.8` 会保持格子那块像素，并在日志里说明这个 scale 没有被应用 |

`--demo` 用测试图代替桌面（`DemoPicture`）：不需要窗口服务器、不需要授权、模型固定，页脚会打出这一帧的测量值。
它存在的原因很直接——上面每一个 bug 在代码里都看不见、在需要 VM 和人的屏幕上却一眼就能看见；测试图自己的边框就是尺子
（TROUBLESHOOTING 23f）。

几何只有一个方向：**格子 → 像素**。旧代码在像素里做 fit、再取整成格子、又把像素算一遍（`originX/originY`、
`pixelWidth/Height`、每秒一次的 `ioctl`、可变的 fallback 格子）；两次取整可以不一致，而每一次"盒子对了、图不对"
的报告，都是那两次取整在打架。

## 8. 代码接缝

1. **`WindowOrder`**（纯函数）：`[CGWindowList 字典] → [窗口]`，过滤 + 排序。用字典 fixture 直接测，
   把上面那对 `Gesture Blocking Overlay` + 真窗口写进用例。
2. **`WallLayout`**（纯函数）：`(pane, displays, windows, per, start) → [行, 图矩形, 说明矩形, 命中表]`。
   矩形同时是"图放哪"和"字放哪"的答案 —— 这是遮罩和版本演进都不会破版的原因。
3. **`PanelDriver`**：可见面板的 tick（主屏 2 s / 其他屏 5 s / 窗口 3 s，错开）、每块缓存上一帧、
   逐块去重、总采集预算。
4. **`ScreenWriter`**：面板用 placement，说明和表头用文本；**文本永不写在 placement 覆盖的格子上**
   （规则写在 `Chrome.swift:9-10`，靠"只画 `chromeTop` 以下的行"结构性保证，没有运行时断言）。
5. **鼠标已经有了**（侦察结论，与设计稿早先的假设相反）：SGR 1006 解析在
   `krdcore/Input.swift:176-243`，格子/像素坐标的判定在 `krd/Input.swift:256-281`，`onChromeClick(cy, cx)`
   送的是 **1-based 的行列**，`Chrome.hitTest` 也在（`Chrome.swift:206`）。`?1002/?1003/?1006/?1016` 早已开启
   （`Render.swift:117-122`）。**所以墙面要做的是"策略"，不是解析器**：把 `hitTest` 的返回值从
   `ChromeHit` 扩成墙面的 `Action`，其余不动。

   **路由判据是"在不在图片矩形里"，不是"在不在 chrome 区"**：`viewport.contains(cell:)` 为真 → 转成远程坐标
   注入（`Input.swift:282`、`Geometry.swift:64-75`）；为假 → `onChromeClick`，直接 return，**永远不会变成远程点击**
   （`Input.swift:277-280`）。这带来一条硬约束：**图片绝不能盖住竖条那一列**，否则点竖条会被当成点远程。
   反过来，图片比面板窄时多出来的那几列天然落进 chrome 分支，是安全的。

   **但今天的 chromeClick 会把点不到控件的点击吞掉**（`.outside` → `break`，`main.swift:1754-1755`），
   竖条必须返回真实动作，不能沿用这个默认。滚轮也会走这条分支（判据只查了 `!motion`），所以墙要自己解释它：
   **滚轮一格 = 一个屏 / 一张卡片**（`WallLayout.wheelAction(row:col:direction:)`），因为拖动是连续手势，
   一页一格会让触控板一划从第一个窗口跳到最后一个；竖条上的 `▲▼` 仍然是"点一下翻一页"。没有可滚的时候返回
   `nil`，那一下滚轮就被墙吃掉而不是去动别的架。
6. **`Desk`**：`wall / focus` 两个视图 + 迁移函数，`focus` 用今天的 `restartCapture`。

**最大的接缝在 placement**：今天没有任何 API 能"把一张图放到任意格子矩形"。`TileGrid.rect` 把原点写死成
`col = 1, row = 1`（`Tiles.swift:52-61`），id 由 `tile.index` 派生（`Render.swift:282-283`），
`emitVariant` 虽然带 `row/col/cols/rows` 但只是诊断用（`f=32`、自己 flush、没有 id 策略）。
墙面需要的就是"矩形 + 稳定 id + 批量发送"这一条新路径——**这是 P2 的主要工作量**。

**采集侧比预想的更硬（侦察结论）**：

- 仓库里**没有任何一次性截图**（`SCScreenshotManager` / `CGWindowListCreateImage` 零命中），
  100% 是 `SCStream`，而且**一个会话只有一个 `Capturer` / 一条流**（`Capture.swift:9-12,60-63`）。
- 缩放在 SCK 里做（`config.width/height` 直接要卡片像素尺寸，`Capture.swift:51-52`），krd 自己没有缩放器
  （`vImageScale`/`CGContext`/`CGImage` 全零命中，只有一次 BGRA→RGB 的通道翻转 `Capture.swift:140-161`）。
  所以"按卡片的像素尺寸拍"是免费的——前提是能开第二条流。
- `handleFrame` **只接受一种尺寸**，别的直接丢（`main.swift:1349-1356`）。墙面 4 块图尺寸各不相同，
  所以不能复用今天的单流路径。
- 流挂了只会汇报并重试 5 次，重试时用的是**旧 filter**（`Capture.swift:66-70`、`main.swift:929-953,1271-1287`）；
  **没有"窗口没了退回整屏"的逻辑**（`reconcileCaptureTarget` 只在显示器变化时跑）。
  → 窗口被关掉时，那块面板就画**遮罩**（§4 的兜底在这里第一次有了真实理由）。

两个已踩过的坑（重启路径）：

- `handleResize` / `restartCapture` 在 `filter == nil` 时是空操作（`main.swift:1429`、`1272`）；
- 搬家时**只能调 `handleResize` 或 `restartCapture` 之一**，第二个会落进 `restartPending`（`main.swift:1273`、`1291`）；
- `makeCaptureTarget` 需要新增 `windowID:` 参数（`options` 是 `let`）；
- `TileGrid.make` 表达不了 0 行（`Tiles.swift:39-40`），`aspect == 0` 会 trap（`:34`）。

## 9. 带宽（本仓库 bench 实测）

`.build/release/krd --bench --json`，2329×1452 px（3.38 MP），上行字节含 base64：

| 内容 | 每 MP | 落地屏（舞台 0.81 + 3 窗 × 0.06 = 0.99 MP） |
|---|---|---|
| 界面（纯色/文字） | 28.6 KB | ≈ 28 KB |
| 渐变壁纸 | 92 KB | ≈ 91 KB |
| 照片 / 视频帧 | 3.83 MB | ≈ 3.8 MB |

- 进来一次 ≈ **28 KB**、4 次采集（多几块屏、多几个窗口都不变，只有一屏 4 张图时会变成 5 次）；之后每次 tick 只重拍变化的那块（≈2–4 KB）；
- 静止后**逐块去重 → 0 B/s**。注意这个 0 只对**文本层**成立：镜像帧路径即便没有脏块，每帧仍会发
  `nudge`（6 B）加同步包裹（16 B）——墙面走的是 tick 而不是帧流，所以不受这部分影响；
- 滚一格只需拍新露出的那 1–3 块（换屏时拍整块舞台），已经有的块直接用缓存重画（不重拍）；
- 想对比：整屏 20 fps 镜像的界面内容 ≈ 1.9 MB/s，照片内容 ≈ 259 MB/s。

## 12. 分期

- **P0 已完成（2026-10-30，在 tart VM `kraal-agent` 上实测）**，三件事都有答案：
  1. **一次性截图存在且够快**：`SCScreenshotManager.captureImage`，显示器 1920×1200 → **25.9 ms**，
     窗口 877×499 → **19.4 ms**、702×679 → **28.7 ms**、360×180 → **18.3 ms**；
     **整墙 4 块 = 92.4 ms**（一次，不是每帧）。连拍 5 次不退化。
  2. **4 条并发 `SCStream` 可行**：同进程 1 显示 + 3 窗口，10 fps 目标，2.3 s 内收到 **23/23/22/22 帧**，
     没有流被饿死或互相踩。所以"4 条小流"是备选方案，但墙面不需要它。
  3. **SCK 只缩放、不拉伸**：1920×1200 的屏要求 1200×300 → 拿到 1200×300，内容占 **x∈[0,480)**
     （= 300×1.6），其余纯黑，**左上角对齐**；要求 400×250（同比例）→ 内容铺满。
     即：**按"内容自己的比例"要尺寸，SCK 给的就是 1:1 的内容**，黑边只在比例不匹配时出现。
  **结论：墙面用 4 次一次性截图，不用流。** 没有帧循环、没有去重、没有流生命周期；墙面变一次
  （1 s tick 发现模型变化）才拍一次，~92 ms，然后压缩上屏。`Capture.swift` 那套一条流的逻辑
  完全不动——P2 是新增一条并行路径，不是改造镜像路径。
- **P1** `WindowOrder` + `WallLayout` + 文本层（先只有文字卡片和无图的框，`--start wall` 显式打开）。
- **P2 已完成（2026-10-30）**：`PanelImage`（fit + 透明合成，纯、可测）、`WallPanels`（计划）、
  `PanelCapture`（一次性截图，具名失败）、`WallPictures`（拍 → 采色 → 合成）、`Render.emitPanel`
  （与贴片同一种线格式，id 由调用方给）、`WallCanvas` 的三种槽位状态（占位 / 图 / 遮罩）。
  实测 137×44：整墙 **4 张图、1.18 MB**、一次；镜像路径的字节数与 golden dump 完全没变。
  去重没有做——墙面本来就只在模型变化时重画，缓存要等真的量到 CPU 是瓶颈再说。
- **P3** 全开 + 滚动 + `⤢` + 鼠标命中。
- **P3 完成（2026-10-30）**：每段都能进、右边竖条（两段、滚轮一格一项、点箭头翻一页）、鼠标命中图、
  一行卡片同高、舞台和卡片之间一条分隔线、卡片之间 3 格间距。
- **P3b 完成（2026-10-30）**：点一张图，这个进程直接**变成** `krd --window <id>`（`execv`，不是 spawn），
  在里面按 `Ctrl-\` 又把墙 `exec` 回来，并停在原来那一页。
  **为什么不用子进程**（第一版就是子进程，只活了一个小时）：同一个可执行文件的两个活进程不能同时当
  ScreenCaptureKit 客户端——后进来的那个流会立刻以 `-3805`（"failed during stream due to application
  connection being interrupted"）死掉。在开发机上四种方式量过：同一个子进程单独跑正常；墙在跑时失败；
  墙在它第一次截图之前就被 `SIGSTOP` 冻住也失败；把同一个二进制拷到另一个路径再启动又正常。撞的是
  可执行文件身份和窗口服务器之间的那一份，所以解法是让客户端只剩一个。
  `exec` 的代价是没人留下来等镜像，于是货架的偏移（`--wall-at <s>:<c>`）和失败的那句话
  （`--said <exit> <text>`）走 argv——换了进程镜像之后唯一能活下来的状态就是它——读者回到的墙会在页脚
  写真原因，而不是一声不响。**首帧都没拿到的流**会立刻带着那句话退出（它指的是一个永远不会打开的
  目标），而不是在冻结的面板后面花五次重试。
  另外 kitty 的 placement 活得比放它的进程长，所以**每个会话开场都先删掉面板里所有的图**
  （`ScreenWriter.clear()`）；而镜像在回墙之前会**先离开备用屏**再 `exec`，因为终端可能把图挂在那块屏上，
  在删除命令已经被应答之后照样继续画（Rex 实测如此，Ghostty 不会）。代价是两个模式之间闪一帧 shell，
  但这是实测唯一有效的做法：墙随后会建一块全新的屏。否则镜像最后那张画面会压在墙的卡片上，
  用户会报成"分辨率变了"（TROUBLESHOOTING 23d）。
- **P4 完成（2026-10-30）**：直接跑 `krd` 进落地屏。`--mirror`（或者 `--window <查询>`——点名要一个窗口，
  它不可能是指墙）拿回原来的默认；`wall` 仍是软链，`--wall` 也仍能解析，因为脚本会这么写。
  `--list`、`--selftest`、`--bench`、`--mock` 走各自的老路：它们都在墙分支之前判定，其中 `--list` 是唯一
  会被吞掉的那个，所以墙分支单独排除了它。

## 13. 什么会改变结论

- 实测发现 z 序与"我最近用的"差得离谱（全屏 App、多 Space）→ 自己记账的 MRU。
- 3 个不够，实际大半时间都在翻页 → 一屏 4–5 个，或者卡片下面加一条剩余窗口的紧凑索引。
- 5 次 tick 有可感知的 CPU/耗电 → 副屏和窗口降到 5–10 s，或未聚焦时不 tick。
- 想省到底 → 大图那块退回遮罩（版式已经保证同矩形，来回切换不跳）。
